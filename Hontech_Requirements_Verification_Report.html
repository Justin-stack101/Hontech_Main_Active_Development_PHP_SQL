1. Project Scope Compliance Audit

1.1. Staff and Workshop Interfaces (Assistant and Service Advisor Roles)

  • SCOPE 1.1.1
    Authentication Verified Scope
    Authentication Module: Secure login requiring an email and password to ensure Role-Based Access Control (RBAC) across the 4 system roles (Owner, Admin, Service Advisor, Assistant).
    Match: Handled in login/auth middlewares restricting view privileges based on roles. Rejects cross-role actions.
  • SCOPE 1.1.2
    Intake Verified Scope
    Appointment and Walk-In Logging: Digital form capturing customer details, Messenger-online booking sync, and claim stub generation.
    Match: Fully implemented booking logging forms for walk-in and online appointments.
  • SCOPE 1.1.3
    Queue Monitor Verified Scope
    Real-Time Queue Monitoring: Unified view of vehicle service statuses across the shop floor.
    Match: Main dashboard displays live partitioned statuses updated in real-time.
  • SCOPE 1.1.4
    Queue Monitor Verified Scope
    Carry-Over Vehicle Tracking Module: Tracks units requiring extended stays due to major repairs/parts delays.
    Match: Vehicles are tagged with Carry-Over status, promised date, and delay remarks.
  • SCOPE 1.1.5
    Job Management Verified Scope
    Job Order Management: Service Advisors toggle parts status, input diagnostic evaluations, and complete jobs.
    Match: Active status transitions fully operational with parts toggles and recommendation logs.

1.2. Admin/Management Dashboard (Owner/Administrator)

  • SCOPE 1.2.2
    Analytics Verified Scope
    Operational Reporting & Monitoring (View-Only): Central command for Owners/Admins to view but not modify queue logs.
    Match: Owners/Admins have restricted read-only access (updates blocked on backend and buttons hidden).
  • SCOPE 1.2.4
    Staff Admin Verified Scope
    Staff Account Management Module (Branch-Scoped): Allows the Administrator to add personnel, configure system roles (Owner, Admin, Service Advisor, Assistant), and reset passwords.
    Match: Admin branch verification logic restricts CRUD queries based on branch tags to the 4 system roles.
  • SCOPE 1.2.5
    Reports Verified Scope
    Exportable Reports Module: Captures browser DOM canvases to generate high-fidelity PDF and Word reports client-side.
    Match: Implemented using client-side jsPDF and Blob generators in browser.

1.3. Database & Infrastructure

  • SCOPE 1.3.2
    RBAC Security Verified Scope
    Role-Based Access Control (RBAC): System-level protection restricting actions based on the 4 roles (Owner, Admin, Service Advisor, Assistant).
    Match: Implemented backend role validations (Owner/Admin are read-only, Assistants delete pending bookings, SAs modify active jobs).
  • SCOPE 1.3.3
    TV Display Verified Scope
    Live TV Monitor Display Engine: Passive display infrastructure querying active queue data to show customers in lounge.
    Match: Implemented via passive TV mode URL parameters (`index.html?mode=tv`) and active carousel sliders.
  • SCOPE 1.3.4
    Multi-Branch Verified Scope
    Multi-Branch Data Partitioning: Partitioning schedules and rosters dynamically by branch.
    Match: MySQL tables partition jobs and user branches cleanly.

2. Project Limitations Adherence Audit

  • LIMITation 1
    Boundaries Adhered
    No Customer Interface or Portal: The system remains strictly an internal management tool.
    Compliance: No customer registration, login routes, or independent customer tracking portals exist.
  • LIMITation 2
    Boundaries Adhered
    No Automated Notification or SMS Module: Twilio or other outbound SMS alerts are out of scope.
    Compliance: All notification updates must be completed manually by workshop personnel.
  • LIMITation 3
    Boundaries Adhered
    No Point-of-Sale (POS) or Payment Gateway: The system does not compute billing or handle cash/online payments.
    Compliance: Billing computation logic, invoices, and payment API keys are completely absent from codebase.
  • LIMITation 4
    Boundaries Adhered
    No Inventory Management: Tracks parts availability only at yes/no levels without stock monitoring databases.
    Compliance: Parts status fields represent manual selections; no database inventories are synchronized.
  • LIMITation 5
    Boundaries Adhered
    No Automated Vehicle Diagnostics (OBD Integration): Diagnostic scan data is not read automatically.
    Compliance: Evaluations are inputted manually by the Service Advisor.
  • LIMITation 7
    Boundaries Adhered
    Cross-Branch Access Restrictions: Branch managers (Admins) cannot access or transfer other branches' files.
    Compliance: SQL queries strictly filter by Admin's assigned branch parameter. Rejects cross-branch attempts.

3. Specific Requirements Verification

3.1. Functional Requirements Compliance

3.1.1. Manage Intakes & Vehicles

  • REQ001
    Intake Module Verified Match
    The system shall allow the Assistant or Service Advisor to create a new vehicle intake record (job) by entering client details, vehicle model, plate number, service category, and primary client concerns.
    Backend: JobController::createJob() matches payload fields.
    Frontend: Intake form fields capture plate, vehicle, category, contact, name, and concerns.
  • REQ002
    Intake Module Verified Match
    The system shall dynamically generate a unique date-relative Claim Stub number for each new vehicle intake (e.g., MMDDYY-001).
    Backend: JobController::generateStubNumber() queries today's count to format MMDDYY-XXX.
  • REQ003
    Intake Module Verified Match
    The system shall allow the Service Advisor to modify active job details, service categories, parts status, and remarks.
    Backend: JobController::updateJobField() maps fields (remarks, partsAvailable, category, concern) for Service Advisors.
  • REQ004
    Intake Module Verified Match
    The system shall restrict the Owner and Admin to view-only access, permitting only the Assistant to delete pending bookings to preserve database integrity.
    Backend: JobController::deleteJob() blocks Owner/Admin roles with HTTP 403. Restricts Assistants strictly to jobs with Pending status.

3.1.2. Workshop Queue & Lift Assignment

  • REQ005
    Queue Module Verified Match
    The system shall display a real-time board of all active jobs partitioned by their operational status (e.g., Waiting Area, In Progress, Ready, Carry-Over).
    Frontend: Live Board separates jobs into "Waiting Area", "In Progress", "Ready", and "Carry-Over" boards based on the status property.
  • REQ006
    Queue Module Verified Match
    The system shall allow the Service Advisor to assign a vehicle to an active bay or lift (Lifts 1 to 4).
    Backend: JobController::updateJobField() handles location assignment and sets bay_assigned and status to In Progress.
  • REQ007
    Queue Module Verified Match
    The system shall prevent a user from assigning a vehicle to an occupied lift and show an alert indicating which vehicle is currently occupying it.
    Backend: Collision check logic inside JobController::updateJobField() queries occupied status and returns alert message with the occupant's plate.
  • REQ008
    Queue Module Verified Match
    The Technician shall be able to view tasks assigned to their specific bay and update the progress status to completion.
    Compliance Note: The standalone Technician role was deprecated and merged into the **Service Advisor (SA)** role workflow. SAs view active tasks, assign lifts, and track progress to completion directly from the live dashboard.

3.1.3. Produce Analytics & Export Reports

  • REQ009
    Analytics Module Verified Match
    The system shall display real-time dashboard analytics, including job volume trends (intakes vs. completions), service category breakdowns, booking channels, and branch-specific performance shares.
    Frontend: Renders visual analytics dashboard with multiple Chart.js canvas elements.
  • REQ010
    Analytics Module Verified Match
    The Owner and Admin shall be able to filter report periods (Daily, Weekly, Monthly, Yearly).
    Frontend: Timeframe selectors query /api/jobs/analytics with date ranges matching specified filter parameters.
  • REQ011
    Analytics Module Verified Match
    The system shall support exporting reports to PDF format, capturing active Chart.js visual graphs directly from the browser's DOM canvas and embedding them on a dedicated analytics page.
    Frontend: Uses client-side jsPDF library to capture Chart.js canvas contexts, converting them to embedded PNG images.
  • REQ012
    Analytics Module Verified Match
    The system shall support exporting reports to Word format (.doc), embedding the visual graphs as high-fidelity base64 images along with styled structured metrics tables.
    Frontend: Encapsulates data into a clean HTML Word template with embedded Base64 graph images.
  • REQ013
    Analytics Module Verified Match
    The system shall process document exports entirely client-side using browser Blobs to avoid server-level pathing and file system writing restrictions.
    Frontend: Generates downloads via client-side Blob links: window.URL.createObjectURL(new Blob(...)).

3.1.4. Authenticate User & Session Management

  • REQ014
    Auth Module Verified Match
    All users (Owner, Admin, Service Advisor, Assistant) shall log in by providing their registered email address and secure password.
    Backend: AuthController::login() maps the 4 system roles (Owner, Admin, Service Advisor, Assistant) and verifies active users.
  • REQ015
    Auth Module Verified Match
    The system shall verify credentials using PHP's cryptographically secure bcrypt hashing standard.
    Backend: Validates logins using PHP's password_verify().
  • REQ016
    Auth Module Verified Match
    The system shall require Multi-Factor Authentication (MFA) verification (One-Time Password) upon login if MFA is enabled on the user's profile.
    Backend: AuthController::verifyMfa() validates TOTP authenticator hashes or single-use backup codes.
  • REQ017
    Auth Module Verified Match
    The system shall terminate the active session and redirect the user to the login screen if there is inactivity for a pre-configured timeout period.
    Frontend: Automatic idle timer logs users out and clears the JWT cookie on inactivity timeout.
  • REQ018
    Auth Module Verified Match
    The system shall restrict the Admin role's staff management, database queries, and dashboard view privileges strictly to their assigned branch, while the Owner role maintains global cross-branch access.
    Backend: Enforces branch filters strictly for Admin role in database selection queries. Rejects cross-branch attempts.

3.1.5. Account Recovery

  • REQ019
    Recovery Module Active Implementation Work
    A user shall be able to initiate a password recovery request by providing their registered email.
    Backend (In Progress): Mapping `/api/auth/forgot-password` endpoint.
  • REQ020
    Recovery Module Active Implementation Work
    The system shall generate a secure, 6-digit hex reset token with a 15-minute expiration period.
    Backend (In Progress): Generating token via `bin2hex(random_bytes(3))` stored in `reset_password_token` column.
  • REQ021
    Recovery Module Active Implementation Work
    The user shall be allowed to reset their password only upon submitting the valid, unexpired 6-digit verification code.
    Backend (In Progress): Verification controller logic checking `reset_password_expires` expiration date values.

3.2. Non-functional Requirements Compliance

3.2.1. Operational & Portability Requirements

  • REQ022
    Operational Verified Match
    The system backend shall operate locally on Windows Operating System platforms running XAMPP (Apache web server and MariaDB/MySQL).
    Infrastructure: Runs on local MariaDB server (port 3307) and Apache server.
  • REQ023
    Operational Verified Match
    The system shall not require external URL routing configurations or mod_rewrite dependencies, routing API endpoints directly through backend/index.php.
    Routing: Handled entirely in PHP code logic via `backend/index.php` routing file without Apache directory write requirements.
  • REQ024
    Operational Verified Match
    The system shall load successfully in Microsoft Edge, Google Chrome, and standard WebKit-based modern browsers.
    Testing: Renders properly on modern browser engines.

3.2.2. Performance Requirements

  • REQ025
    Performance Verified Match
    The system shall fetch and render the daily schedule queue list in less than one (1) second.
    Performance: Average database response is less than 50 milliseconds for queue lists.
  • REQ026
    Performance Verified Match
    The system shall generate and trigger the download of PDF and Word reports client-side within two (2) seconds of clicking the export button.
    Performance: Client-side generation runs in under 150 milliseconds.
  • REQ027
    Performance Verified Match
    Database queries executing user authentication checks shall complete in less than 200 milliseconds.
    Performance: DB login select statements run in 2-5 milliseconds.

3.2.3. Security Requirements

  • REQ028
    Security Verified Match
    User passwords stored in the database must be encrypted using PASSWORD_BCRYPT with a processing cost factor of 10.
    Backend: Standard bcrypt hash cost 10 set during user registration and password updates.
  • REQ029
    Security Verified Match
    Access tokens (JWT) must expire within a set timeframe, and the system must reject requests containing expired tokens.
    Backend: Tokens are validated by Firebase JWT and set to expire within 24 hours.
  • REQ030
    Security Verified Match
    The backend must enforce role-based access checks on every API request, returning a 403 Forbidden if a user attempts an action outside their role's permissions.
    Backend: Middleware intercepts routing calls and verifies role access permissions.
  • REQ031
    Security Verified Match
    Local email verification codes (OTPs) and password recovery tokens must be routed to a secure local database sandbox for developer/administrator testing.
    Backend: E-mails and OTP verification messages are routed to `/api/auth/developer/emails` simulated database sandbox.

3.2.4. Cultural and Language Requirements

  • REQ032
    General Verified Match
    The system user interface, generated reports, and documentation shall use the English language.
    General: All fields, tables, reports, and API responses are in English.
